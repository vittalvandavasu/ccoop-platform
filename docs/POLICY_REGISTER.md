## Current meanings in code

`obligations.amount` is an immutable amount requested for a particular order/provider. `payment_events.amount` is a verified receipt; `credited_amount` is the portion applied to the order, and `orders.paid` is accumulated applied paise. `payment_exceptions` records verified receipts not applied under existing rules. `orders.payment_hold` blocks new payments and handover; it is not a wallet balance or a provider escrow API. `captured` means receipt evidence exists, not that funds were applied, refunded or settled to the merchant's bank. A job being DONE says nothing about provider settlement to a bank. No student credit wallet, refund request/execution API or generic hold-release API exists. Stock on_hand/allocated and movements are separate from money; discrepancy notes cannot change them.

Every entry uses the table's question/context, options/tradeoffs, recommendation and approving role, plus the shared controls below. All implementation dependencies include explicit approval and targeted authorization, concurrency, replay, audit and recovery tests. No disposition can overwrite original events, obligations, receipts or movements.

## Approval record template and shared controls

### Replacement decision RP-01 — PROPOSED / NOT APPROVED

Question: when may missing, damaged or incorrectly delivered units be replaced rather than refunded or held for supplier correction? Context: current orders support whole-order allocation/handover, and no replacement order lineage exists. Options: (A) retain hold pending supplier correction (preserves current model but delays students); (B) issue a linked replacement after independent evidence/approval (better service but adds stock, shipping and duplicate-compensation risk); (C) offer an approved refund instead (closes fulfillment need but has provider/fee consequences). Engineering recommendation: retain existing holds until product/finance/fulfillment approve the customer-choice and ownership rules; if B is chosen, use explicit original-order/unit lineage, never silently clone a payable order or rewrite the commercial snapshot.

Required evidence: original receipt and pickup state, damaged/incorrect/missing-unit findings, customer acceptance, supplier responsibility and verified available replacement stock. Authorization: named fulfillment supervisor with finance approval where valuation/refund exposure changes; separation/limits require business approval. Audit: preserve original receipt, payment and handover history; append reason, approvers, source units, replacement identity, stock movement and delivery outcome. Prevent replacement plus refund or repeat replacement for the same disposition unless separately authorized. Dependencies: RF-05/RF-07, ST-01/02/03/06/07 and CR-02; packing/per-unit handling and compensation reconciliation need approved design/tests. No replacement or partial-fulfillment behavior is enabled by this recommendation.

For each ID record: chosen option and limits; named approver and role; date; business rationale; approved evidence/retention; monetary/stock consequences; customer communications; escalation/exception rule; implementation owner; dependencies; acceptance tests; effective environment. Until filled and approved, status stays PROPOSED / NOT APPROVED. Recommended role separation/thresholds are not implemented permissions.

Engineering safeguards for any later implementation: server-side scoped authorization, immutable source references, integer paise, atomic state/ledger/audit transaction, payload-bound idempotency, concurrency locks in existing order, evidence revision checks, independent provider confirmation, sanitized error states, bounded retries and reconciliation. Do not introduce a parallel ledger casually; extend the existing model only through an approved design/migration. Customer notice and legal/tax treatment require authorized specialist review, not assumptions in code.
